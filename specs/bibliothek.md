# Schnittstelle der Bibliothek

## Zweck

Was ein Programm, das `sdb_reader` benutzt, von der Bibliothek erwarten kann:
welche Namen zugesagt sind, wie es eine Datei liest, wie es einen einmal
gelesenen Text aufbewahrt, woran es erkennt, dass eine aufbewahrte Lesung
veraltet ist, und wie es unter mehreren Blättern das geltende findet. Wie die Bibliothek ein Blatt liest, regelt
`sicherheitsdatenblatt.md`, was die Befehlszeile ausgibt, `sdb-werkzeug.md`.

## Begriffe

- **Aufrufer:** ein Programm, das die Bibliothek importiert.
- **Text einer Datei:** was die Lese-Stufe aus einer PDF-Datei gewinnt
  (SDB-42 bis SDB-46), mit dem Verfahren, der Zahl der gelesenen Seiten und
  ihren Warnungen.
- **Lesung:** was die Bibliothek zu einer Datei sagt: der Text, das Urteil,
  was für ein Dokument sie ist, und für ein deutsches Sicherheitsdatenblatt
  dessen Angaben.
- **Lese-Stufe:** der Teil, der aus der Datei den Text macht.
  **Parse-Stufe:** der Teil, der aus dem Text die Lesung macht.

## Regeln

- **BIB-1.** Zugesagt sind die Namen, die das Paket `sdb_reader` selbst exportiert, und nur sie. Jeder trägt eine Beschreibung. Was nur über ein Untermodul zu erreichen ist, kann sich ohne Ankündigung ändern; das gilt auch für die Teile, die ein Sprachmodell fragen und zwei Läufe vergleichen: `ask` und `diff` sind Funktionen der Befehlszeile (SDW-25 bis SDW-28), für die das Paket keine Namen exportiert.
- **BIB-2.** Die Bibliothek liest eine Datei allein nach ihrem Inhalt. `read_sheet` nimmt den Pfad der Datei und nichts, was ein Aufrufer sonst über sie weiß: kein Produkt, keinen Lieferanten, keine Vermutung, was für ein Dokument sie ist. Die Lesung nennt die Datei nicht; sie ihr zuzuordnen, ist Sache des Aufrufers.
- **BIB-3.** Ein Aufrufer kann den Text einer Datei aufbewahren und später ohne die Datei lesen: `extraction_to_dict` gibt den Text in einer Form, die sich als JSON speichern lässt, `extraction_from_dict` liest sie zurück, und `read_extraction` ergibt daraus dieselbe Lesung wie `read_sheet` aus der Datei. Aufbewahrt werden der Text, das Verfahren, die Zahl der gelesenen Seiten und die Warnungen, dazu die Lese-Stufe, aus der der Text stammt (BIB-4), und für einen Text aus der Texterkennung die Version des Programms `tesseract`, mit der er gelesen wurde (SDB-116); der Text vor dem Bereinigen und die einzelnen Seiten nicht. Die Warnungen der Lese-Stufe stehen im aufbewahrten Text als Code und Angaben, ohne Satz (BIB-10). Ein Text, der sie noch als Satz trägt, weil er vor den Codes aufbewahrt wurde, wird weiter gelesen: Jeder der damaligen Sätze bekommt seinen Code, ein unbekannter den Code `unknown` mit dem Satz als Angabe. Ebenso eine Warnung, deren Code diese Fassung nicht kennt oder deren Angaben nicht zu ihm passen, weil eine andere Fassung den Text aufbewahrt hat: Ein aufbewahrter Text lässt sich immer zurücklesen.
- **BIB-4.** Die Bibliothek nennt für jede Stufe eine Version, eine ganze Zahl. `EXTRACTION_VERSION` steigt mit jeder Änderung, nach der dieselbe Datei einen anderen Text ergeben kann, `PARSER_VERSION` mit jeder Änderung, nach der derselbe Text eine andere Lesung ergeben kann. Eine Version sinkt nie. Der Text hängt auch von der PDF-Bibliothek ab: `extraction_stage()` nennt die Version der Lese-Stufe zusammen mit der der PDF-Bibliothek, und mit ihr vergleicht ein Aufrufer, ob ein aufbewahrter Text noch gilt.
- **BIB-5.** Wer den Code einer Stufe ändert, entscheidet über ihre Version: Ein Test hält für jede Stufe einen Fingerabdruck ihres Codes fest und schlägt fehl, wenn er sich ändert, bis der Fingerabdruck erneuert ist. Kommentare, Beschreibungen und Formatierung ändern ihn nicht.
- **BIB-6.** `current_state` wählt unter den Blättern eines Produkts das geltende. Sie bekommt je Blatt nur Angaben (`SheetState`: Überarbeitungsdatum, Ausgabedatum, Version wie gedruckt, genannte Länder) und liest keine Datei; woher die Angaben stammen und welche Blätter zusammengehören, ist Sache des Aufrufers. Das Ergebnis (`Choice`) nennt die Position des geltenden Blatts in der übergebenen Reihenfolge und den Grund. Ohne Angaben gibt es kein Ergebnis, sondern einen Fehler.
- **BIB-7.** Es gilt das Blatt mit dem jüngsten Überarbeitungsdatum; bei gleichem Datum eines, das das gewünschte Land nennt, dann das mit der höheren Version, dann das mit dem jüngeren Ausgabedatum, zuletzt das spätere in der übergebenen Reihenfolge. Ein fehlendes Datum gilt als das älteste, eine fehlende oder nicht lesbare Version als die niedrigste. Lesbar ist eine Version aus Zahlen, die Punkte trennen; verglichen werden die Zahlen, nicht die Zeichen.
- **BIB-8.** Nennt das nach BIB-7 gewählte Blatt Länder und das gewünschte nicht, und nennt ein anderes das gewünschte Land, gilt statt seiner das nach BIB-7 erste dieser Blätter, wenn beide eine lesbare Version tragen und die des Blatts für das gewünschte Land nicht niedriger ist (Grund `stands-in`, mit der Position des verdrängten Blatts). Ist sie niedriger, fehlt einem der beiden die lesbare Version oder nennt kein Blatt das gewünschte Land, bleibt es beim gewählten Blatt (Grund `other-country`). Ein Blatt, das kein Land nennt, gilt für das gewünschte Land (Grund `newest`).
- **BIB-9.** Das gewünschte Land gibt der Aufrufer an; voreingestellt ist `DE`. Ohne gewünschtes Land spielen die genannten Länder keine Rolle, und es entscheiden Datum, Version, Ausgabedatum und Reihenfolge.
- **BIB-10.** Alles, was die Bibliothek zu einer Datei anmerkt, ist eine Meldung mit einem festen Code und benannten Angaben: die Warnungen der Lese-Stufe, der Prüfung und des Parsers, die Gründe, aus denen sich eine Datei nicht lesen lässt, und die Befunde zu einem Blatt. Der Code ist ein kurzes englisches Kennwort in Kleinbuchstaben mit Bindestrichen (`pictograms-derived`), die Angaben tragen, was die Meldung nennt (`{"pictograms": ["GHS07"]}`), in Typen, die sich als JSON schreiben lassen; ein Datum steht als Zeichenfolge in der Form `JJJJ-MM-TT`. Die Codes und die Namen ihrer Angaben gehören zur Schnittstelle (BIB-1): Die Bibliothek führt sie in einer Liste, ein Code bekommt nie eine andere Bedeutung, und einer, der entfällt, wird nicht neu vergeben.
- **BIB-11.** Den Satz zu einer Meldung liefert ein Katalog je Sprache: eine Textdatei, die jedem Code einen Satz mit Platzhaltern für seine Angaben zuordnet. Für eine Meldung, die etwas zählt (Seiten, Blätter, Abschnitte), kann der Katalog zwei Sätze geben, `one` für genau eins und `other` für jede andere Zahl; welche Angabe zählt, legt die Bibliothek je Code fest. Ein Katalog sagt in einer Zeile, wie er ein Datum schreibt (`[format]`, `date`); ohne sie steht es, wie die Meldung es trägt. Die Angaben der Meldung ändert das nicht: Sie sind für Programme. Die Bibliothek liefert Englisch und Deutsch mit; ein Test hält fest, dass jeder mitgelieferte Katalog jeden Code und jede Angabe kennt. Ein Aufrufer wählt die Sprache ausdrücklich, voreingestellt ist Deutsch; die Sprache des Rechners spielt keine Rolle, damit dieselbe Datei überall dieselbe Ausgabe ergibt. Für eine Sprache, zu der kein Katalog mitgeliefert wird, gibt es keinen Satz, sondern einen Fehler. Er kann einen eigenen Katalog als Datei angeben; fehlt darin ein Code, gilt für ihn der englische Satz.
- **BIB-12.** Die Bibliothek entscheidet nie nach dem Wortlaut einer Meldung, sondern nach ihrem Code und ihren Angaben, und ein Aufrufer muss es ebenso wenig: Was bis Version 0.2 aus dem Text einer Warnung gelesen wurde (die Einstufung „nicht bestimmt“, die Einstufung nach altem Recht, ein EUH-Satz außerhalb der Kennzeichnung), steht in der Meldung als Code und Angabe.
- **BIB-13.** Ab Version 1.0 folgen die Versionen der semantischen Versionierung. Die Hauptnummer steigt mit einer brechenden Änderung: an einem exportierten Namen (BIB-1), an einem Code oder seinen Angaben (BIB-10), am JSON-Schema (BIB-15) oder an den Optionen und Exit-Codes der Befehlszeile. Die Nebennummer steigt mit einer Erweiterung und mit jeder Erhöhung von `EXTRACTION_VERSION` oder `PARSER_VERSION` (BIB-4), weil ein Aufrufer danach neu lesen muss. Die Patch-Nummer steigt mit einer Korrektur, die keine Lesung ändert. Vor 1.0 kann eine Nebenversion brechen; das Änderungsprotokoll sagt es (BIB-18).
- **BIB-14.** Ein exportierter Name, der entfallen soll, bleibt eine Nebenversion lang erhalten und warnt bei seiner Benutzung (`DeprecationWarning`), bevor ihn die nächste Hauptversion entfernt.
- **BIB-15.** Das JSON-Schema der Ausgabe (`sdb-werkzeug.md`, SDW-16) gehört zur Zusage und beschreibt sie nicht nur: Eine Änderung, nach der ein bisher gültiger Datensatz ungültig wird oder ein Schlüssel entfällt, ist brechend (BIB-13).
- **BIB-16.** Unterstützt wird jede Python-Version, die ihre Entwickler zum Zeitpunkt einer Veröffentlichung der Bibliothek noch pflegen, von 3.12 an: derzeit 3.12 bis 3.15. Eine Version scheidet aus, wenn ihre Pflege endet, und eine neue kommt dazu, wenn sie veröffentlicht ist; beides ist keine brechende Änderung (BIB-13). Das Paket nennt die älteste unterstützte Version (`requires-python`) und jede unterstützte in seinen Angaben (`classifiers`), und die Tests laufen mit jeder von ihnen. Andere Python-Versionen sind nicht zugesagt.
- **BIB-17.** Korrekturen bekommt nur die neueste Veröffentlichung. Eine ältere wird nicht nachgepflegt.
- **BIB-18.** Das Änderungsprotokoll (`CHANGELOG.md`) nennt für jede Veröffentlichung, was sich für Aufrufer ändert: jede brechende Änderung unter „Breaking“ und jede Erhöhung einer Stufen-Version, mit dem, was ein Aufrufer mit aufbewahrten Texten und Lesungen tun muss. Es beginnt mit einem Abschnitt „Unreleased“ für das, was seit der letzten Veröffentlichung dazukam; jeder Abschnitt einer Veröffentlichung trägt ihre Version und ihr Datum, der oberste die Version des Pakets. Vor der ersten Veröffentlichung steht dort nur „Unreleased“; der Abschnitt sagt dann, was die erste Version bietet, und nennt die beiden Stufen-Versionen, mit denen sie liest.
- **BIB-19.** Die Bibliothek liest keine Uhr. Was vom heutigen Tag abhängt, bekommt ihn als Angabe des Aufrufers (`today`), und ohne sie hängt kein Ergebnis vom Tag ab. `current_state` behandelt mit dieser Angabe ein Überarbeitungs- oder Ausgabedatum, das nach dem Tag liegt, wie ein fehlendes (BIB-7: als das älteste), jedes der beiden für sich: Ein Blatt mit einem unmöglichen Datum ist deshalb nicht das neueste, und es gilt nur, wenn kein anderes ein Datum trägt und Land, Version, Ausgabedatum und Reihenfolge für es entscheiden. `sheet_findings` und `reading_to_dict` nehmen dieselbe Angabe für die Befunde (`sicherheitsdatenblatt.md`, SDB-137). Die Angabe ist eine Erweiterung im Sinn von BIB-13: Wer sie nicht übergibt, bekommt dasselbe wie zuvor.
- **BIB-20.** Was die Blätter einer Datei übereinander sagen (`sicherheitsdatenblatt.md`, SDB-139), meldet `sheet_findings`, wenn der Aufrufer ihr die Einzelblätter übergibt (`parts`, wie `ParsedSheet.parts` sie nennt); ohne sie bleibt ihr Ergebnis, wie es war. `reading_to_dict` übergibt sie. Das Deckblatt einer Datei (SDB-138) steht am Ergebnis des Parsers (`ParsedSheet.cover_page`, `ParsedSheet.display_term`). Beides sind Erweiterungen (BIB-13). Eine Funktion, die aus den Blättern einer Datei das für ein Land geltende wählt, gibt es noch nicht.
- **BIB-21.** Was die Bibliothek über ein Blatt urteilt, urteilt sie über das Blatt als Ganzes: `requires_sheet` und `contradicts_label` nehmen ein `SafetyDataSheet`, wie `sheet_findings`, und keine einzelnen Angaben. Wer ein Blatt aufbewahrt hat, wie `sheet_to_dict` es gibt, liest es mit `sheet_from_dict` zurück und bekommt dasselbe Blatt; `content_hash` und `sheet_required` gehören nicht zum Blatt und bleiben dabei weg, ein Schlüssel, den diese Fassung nicht kennt, auch. Fehlt einem aufbewahrten Blatt ein Schlüssel oder trägt einer einen Wert anderer Art, stammt es aus einer anderen Fassung: `sheet_from_dict` lehnt es mit einem Fehler ab (`ValueError`) und rät nicht. Ob ein aufbewahrtes Blatt noch gilt, vergleicht der Aufrufer wie bisher an `PARSER_VERSION` (BIB-4); ein veraltetes liest er aus dem aufbewahrten Text neu (BIB-3).
- **BIB-22.** Die Dokumentation steht im Netz unter `https://foerdebaumarkt.github.io/sdb-reader/`, je veröffentlichter Version eine Ausgabe: unter `<Version>/` die einer Version, unter `latest/` die der neuesten; die Adresse selbst führt zur neuesten, und `versions.html` nennt alle. Eine Ausgabe enthält die Seiten unter `docs/`, das Änderungsprotokoll (BIB-18) und die Referenz der exportierten Namen (BIB-1). Sie ist aus dem Stand ihres Tags gebaut und wird danach nicht neu gebaut: Die Ausgabe einer Version ändert sich nicht mehr. Die Regeln unter `specs/` stehen nicht auf den Seiten, sondern im Repository; ein Verweis von einer Seite in das Repository führt zum Stand des Tags, für den die Ausgabe gebaut ist. Das Paket nennt die Adresse in seinen Angaben (`Documentation`). Erzeugte Seiten liegen nicht im Repository.
- **BIB-23.** Eine Veröffentlichung ist ein Tag `v<Version>` auf dem Hauptzweig. Seine Version ist die des Pakets (`pyproject.toml`) und die oberste des Änderungsprotokolls (BIB-18); ein Tag, für das das nicht gilt, wird nicht veröffentlicht. Aus dem Tag baut das Repository selbst das Paket, prüft es und legt es unter dem Namen `sdb-reader` im Python Package Index ab; von Hand wird kein Paket abgelegt. Die erste veröffentlichte Version ist 0.9.0, eine ältere wird nicht veröffentlicht. Solange das Repository nicht öffentlich ist, verlässt nichts das Repository: kein Paket geht an den Index, keine Seite ins Netz (BIB-22).

## Entscheidungsprotokoll

- **2026-11-19**: Die Dokumentation steht als Website im Netz, je Version eine Ausgabe (BIB-22). So wurde es entschieden. Grund: Wer das Paket aus dem Index installiert, hat das Repository nicht vor sich; Anleitung und Referenz gehören an einen Ort, den das Paket nennt. Gebaut wird mit Sphinx aus den Markdown-Seiten, wie sie sind, damit sie im Repository lesbar bleiben; die Referenz der exportierten Namen baut Sphinx aus denselben Beschreibungen im Code, damit sie Teil derselben Website ist, mit deren Kopf, Navigation und Suche. Sie bleibt so streng wie vorher mit `pdoc`: Eine Beschreibung, die sich nicht darstellen lässt, lässt den Bau scheitern, und ebenso ein exportierter Name, der in der Referenz fehlt oder nichts über sich sagt, oder ein Name dort, der nicht exportiert ist. Jede Veröffentlichung trägt ihre gebaute Ausgabe als Datei, und die Website wird aus diesen Dateien zusammengesetzt statt aus den Tags neu gebaut: So liegt nichts Erzeugtes im Repository, und eine alte Ausgabe kann weder sich ändern noch eine spätere Veröffentlichung scheitern lassen, weil ihr Bau nach Jahren nicht mehr gelingt. Das Schaubild in „How it works“ zeigt die Website als Text: Es zu zeichnen, verlangte ein Skript von einem fremden Server bei jedem Aufruf.
- **2026-11-19**: Veröffentlicht wird aus einem Tag durch das Repository selbst, zuerst als Version 0.9.0 (BIB-23). So wurde es entschieden. Grund: Ein von Hand gebautes Paket lässt sich nicht auf einen Stand zurückführen; der Index nimmt das Paket deshalb nur von dem Ablauf des Repositorys an, ohne hinterlegtes Passwort. 0.9.0 und nicht 1.0.0, weil außer einem Aufrufer noch niemand die Schnittstelle benutzt hat und vor 1.0 eine Nebenversion brechen darf (BIB-13). Dass nichts das Repository verlässt, solange es nicht öffentlich ist, steht in der Regel, weil der Ablauf schon vor der Veröffentlichung im Repository liegt und ein versehentlich gesetztes Tag sonst ein Paket in die Welt setzte, das sich nicht zurückholen lässt.
- **2026-11-19**: Das Änderungsprotokoll beginnt mit der ersten öffentlichen Version neu (BIB-18). Grund: Es sagt, was sich für jemanden ändert, der das Paket benutzt; die Stände davor waren nicht veröffentlicht, und ihre Umbenennungen hat kein Aufrufer je gesehen. Bis zur ersten Veröffentlichung steht deshalb nur „Unreleased“ da, mit dem, was die erste Version bietet, und ihren Stufen-Versionen; die Regel, dass jede brechende Änderung und jede Erhöhung einer Stufe genannt wird, gilt von da an unverändert.
- **2026-11-19**: Die exportierten Namen sind vor der ersten öffentlichen Version bereinigt (BIB-1, BIB-21). Die Liste wurde so entschieden. `SDSParserResult`, `SDSVerificationResult` und `SDSSection` heißen `ParsedSheet`, `Verification` und `Section`, weil kein anderer Name das Präfix trug; `ContactInfo.email` heißt `supplier_email`, `HazardStatements.supplemental_phrases` heißt `supplemental_codes`, die Werte von `Section` heißen `section_1` bis `section_16`, `get_pictograms` heißt `pictograms_for`, und der Schalter `fallback` von `extract_pdf_text` heißt `ocr`, weil er genau die Texterkennung ab- und anschaltet. `Verification` trägt nur noch das Urteil (`kind`, `errors`, `warnings`, `prints_statement_codes`); `is_sds` sagte dasselbe wie `kind`, und `confidence` und `indicators` waren Zwischenwerte der Prüfung, die als Zusage nicht mehr zu ändern gewesen wären. `extract_h_codes` und `lacks_annex_ii_2020` sind nicht mehr exportiert: Die erste rief niemand, auch die Bibliothek nicht, und sie ist gelöscht; die zweite ist ein Teil von `sheet_findings`. Grund für alles: Nach 1.0 ginge jede dieser Änderungen nur als Bruch mit einer Hauptversion. BIB-14 gilt ab 1.0; diese Namen gehen ohne Warnung und ohne Übergangsnamen, und das Änderungsprotokoll nennt jeden unter „Breaking“ mit seinem neuen.
- **2026-11-19**: `requires_sheet` und `contradicts_label` nehmen das Blatt statt eines Wörterbuchs, und `sheet_from_dict` liest ein aufbewahrtes Blatt zurück (BIB-21). Grund: Die beiden nahmen ein beliebiges Wörterbuch und einen Wert ohne Typ, damit ein Aufrufer sie mit aufbewahrten Datensätzen rufen konnte; jede andere Funktion nimmt die Typen der Bibliothek, und welche Schlüssel das Wörterbuch tragen musste, stand nirgends. Mit `sheet_from_dict` ist der Weg vom Datensatz zum Urteil ausdrücklich. Ein Datensatz anderer Form wird abgelehnt und nicht gedeutet: Ein Urteil über ein halb gelesenes Blatt wäre still falsch.
- **2026-11-19**: Unterstützt werden die Python-Versionen, die noch gepflegt werden, von 3.12 an (BIB-16). So wurde es entschieden; es ersetzt „nur die neueste“ vom 17.11.2026. Grund: Wer eine öffentliche Bibliothek einbindet, arbeitet meist nicht auf der neuesten Version, und „nur die neueste“ schlösse die meisten aus. Die Grenze nach unten ist fest gewählt, nach oben und über die Zeit gilt, was die Python-Entwickler pflegen: So muss niemand entscheiden, wann eine Version geht. Der Preis ist, dass der Code nichts verwendet, was 3.12 nicht kennt, und dass die Tests je Version laufen.

- **2026-11-18**: Die Befunde über mehrere Blätter einer Datei kommen über `sheet_findings` mit einer weiteren Angabe, nicht über eine neue Funktion (BIB-20). Grund: Ein Aufrufer, der Befunde will, ruft schon diese Funktion; eine zweite hätte er zu kennen und könnte sie vergessen. Die Angabe ist freiwillig, damit kein Aufruf von bisher sich ändert.
- **2026-11-18**: Der heutige Tag ist eine Angabe des Aufrufers (BIB-19). Grund: Ein Datum in der Zukunft soll bei der Wahl des geltenden Blatts und bei den Befunden nicht zählen; dafür muss die Bibliothek wissen, welcher Tag ist. Eine eigene Uhr machte jedes Ergebnis vom Tag des Aufrufs abhängig und ließe sich nicht prüfen. Als Angabe bleibt die Funktion eine von reinen Daten, und ein Aufrufer kann einen Stichtag wählen.
- **2026-11-17**: Die Bibliothek sagt zu, wie sie sich ändert (BIB-13 bis BIB-18). Der Vorschlag wurde so entschieden. Grund: Wer die Bibliothek einbindet, muss wissen, worauf er bauen kann, bevor sie öffentlich wird; bisher stand nur fest, was zur Schnittstelle gehört, nicht, wie sie sich ändern darf. Eine Erhöhung einer Stufen-Version ist eine Nebenversion und keine Korrektur, weil sie einem Aufrufer Arbeit macht, auch wenn kein Name sich ändert. Das Schema ist Teil der Zusage, weil für die meisten Nutzer die Ausgabe die Schnittstelle ist. Nur die neueste Python-Version und nur die neueste Veröffentlichung, weil ein kleines Projekt mehr nicht ehrlich zusagen kann; wer eine ältere braucht, bleibt auf dem Tag, auf dem er baut.
- **2026-11-17**: Ein Katalog kann Einzahl und Mehrzahl unterscheiden und sagt, wie er ein Datum schreibt (BIB-10, BIB-11). Grund: Die Sätze lauteten „1 Seiten angesehen“ und „Überarbeitet am 2019-05-02, vor dem 01.01.2021“. Zwei Sätze je Meldung statt einer Formel im Satz, weil ein Katalog eine Textdatei bleibt, die jemand ohne Programmierkenntnis schreibt und ein Test vollständig prüfen kann; mehr als Einzahl und Mehrzahl brauchen Deutsch und Englisch nicht, und eine Sprache mit mehr Formen bekommt sie, wenn ein Katalog für sie kommt. Das Datum bleibt in den Angaben in der Form `JJJJ-MM-TT`, damit ein Programm es in jeder Sprache gleich liest; nur der Satz zeigt es, wie man es in seiner Sprache schreibt.
- **2026-11-17**: Ein aufbewahrter Text mit einer Warnung, die diese Fassung nicht kennt, wird gelesen und nicht abgelehnt (BIB-3). Grund: Codes können entfallen (BIB-10), und ein Aufrufer bewahrt Texte über Fassungen hinweg auf. Lehnte `extraction_from_dict` einen solchen Text ab, scheiterte genau das Lesen, mit dem der Aufrufer ihn erneuern will.
- **2026-11-17**: Aufbewahrte Texte aus der Zeit vor den Codes bleiben lesbar (BIB-3). Grund: Den Text einer Datei zu gewinnen, ist der teure Teil einer Lesung; eine Änderung an der Form der Warnungen soll niemanden zwingen, einen Bestand neu zu lesen. Die Version der Lese-Stufe steigt deshalb nicht: Dieselbe Datei ergibt denselben Text.
- **2026-11-17**: Meldungen bekommen Codes, ihre Sätze kommen aus Katalogen (BIB-10 bis BIB-12). Grund: Warnungen sind heute freie englische Sätze, und die Befunde werden zum Teil aus ihrem Wortlaut gewonnen; wer einen Satz ändert oder übersetzt, ändert damit ein Ergebnis. Mit einem Code hängt ein Programm an etwas, das in jeder Sprache gleich ist, und der Satz ist nur noch Darstellung. Kataloge als einfache Textdateien statt gettext, weil es einige Dutzend Meldungen sind: Eine weitere Sprache ist eine weitere Datei, ohne Übersetzungs-Build, und die Vollständigkeit prüft ein Test. Die Sprache wird ausdrücklich gewählt, weil die Bibliothek für dieselbe Datei immer dasselbe ergeben soll. Die Nutzer sind überwiegend deutsch, deshalb ist Deutsch die Voreinstellung (entschieden am 17.11.2026); ein Programm, das englische Sätze will, sagt es. Für sein Urteil braucht es die Sätze nicht, dafür sind die Codes da. Die Änderung bricht die Ausgabe und kommt deshalb vor der ersten öffentlichen Version.
- **2026-11-17**: Die Wahl des geltenden Blatts gehört zur Bibliothek, als Funktion über reine Angaben (BIB-6). Grund: Wer mehrere Blätter eines Produkts liest, steht immer vor derselben Frage, und die Antwort hat Fallen, die jeder Aufrufer sonst einzeln findet. Die Funktion liest keine Datei und kennt keine Lesung, damit sie auch für Angaben aus anderer Quelle taugt und BIB-2 gilt.
- **2026-11-17**: Das Datum führt, nicht die Version (BIB-7). Grund: Versionszählungen sind je Lieferant eigen und beginnen neu: 6.00 von 2019 steht dann neben 1.05 von 2025, und die Version voran wählte das ältere Blatt. Ein Datum sagt überall dasselbe.
- **2026-11-17**: Ein jüngeres Blatt für ein anderes Land verdrängt das Blatt für das gewünschte Land nur mit einer höheren Version (BIB-8). Grund: Lieferanten führen je Land eine eigene Reihe und geben denselben Stand mit Versatz aus, „Version 2 / DE“ ein Jahr vor „Version 2 / CH“. Fehlt einem der beiden die Version, bleibt es beim jüngeren Blatt: Blätter eines Stands haben dasselbe Format, eine fehlende Version deutet also auf einen Fehler im Blatt, und der Aufrufer erfährt ihn über den Grund `other-country`.
- **2026-11-17**: Gewählt wird nach dem Land, nicht nach der Sprache (BIB-9). Grund: Rechtlich zählt, für welches Land ein Blatt ausgestellt ist; die Sprache folgt daraus, und Blätter für Deutschland, Österreich und die Schweiz sind alle deutsch.
- **2026-11-16**: Öffentlich ist, was das Paket exportiert (BIB-1). Grund: Bisher hieß „öffentlich“ nur „ohne Unterstrich“, und das trifft auf viele Hilfsfunktionen zu. Eine Liste an einer Stelle ist eine Zusage, die sich prüfen und dokumentieren lässt; die Module darunter bleiben frei für Umbauten.
- **2026-11-16**: Die Bibliothek nimmt nur den Pfad (BIB-2). Grund: Sie trug einen „Kandidaten“ mit Angaben, die sie selbst nie las, weil ein Aufrufer sie aus seinen Dateinamen gewann. Solche Angaben gehören dem Aufrufer; in der Schnittstelle legen sie jeden anderen auf dessen Ablage fest.
- **2026-11-16**: Lesen aus aufbewahrtem Text ist ein eigener Einstieg (BIB-3). Grund: Den Text zu gewinnen, kostet fast die ganze Zeit einer Lesung, die Texterkennung vor allem; Prüfen und Parsen kosten Millisekunden. Wer den Text aufbewahrt, liest nach einer Änderung am Parser einen ganzen Bestand in Sekunden neu.
- **2026-11-16**: Zwei Versionen statt einer (BIB-4). Grund: Eine Änderung am Parser macht keinen aufbewahrten Text ungültig, eine an der Lese-Stufe jeden. Eine gemeinsame Version würde nach jeder Parser-Änderung alle Dateien neu lesen lassen.
- **2026-11-16**: Ein Test erzwingt die Entscheidung über die Version (BIB-5). Grund: Eine Zahl, die von Hand zu erhöhen ist, wird vergessen, und eine vergessene Erhöhung lässt Aufrufer veraltete Lesungen behalten, ohne dass es jemand merkt. Der Fingerabdruck entscheidet nicht selbst, ob die Version steigt, weil nicht jede Änderung am Code das Ergebnis ändert; er sorgt nur dafür, dass gefragt wird.

## Offene Fragen

- **Die Texterkennung** (`tesseract`) geht nicht in `extraction_stage()` ein: Ihre Version steht am Text, den sie gelesen hat (SDB-116), nicht in der Stufe, weil sie nur Scans betrifft und von Rechner zu Rechner verschieden ist. Ob ein aufbewahrter Scan mit einer anderen Version neu gelesen wird, entscheidet der Aufrufer.
